# Demo and advanced modes with licences kept in Keycloak

Status: Accepted by the owner, Yoshikemolo, on 2026-09-23. The owner chose the modes,
the Admin menu and keeping licences in Keycloak; an agent wrote this record.

## Context

The owner wants the current editor to stay open to everyone as a demo, and the advanced
capabilities (AI Tools, change control and later ones) to require registration, a
licence limited in time and permissions. The owner, as administrator, manages users and
licences from an Admin menu: issues licences and sets or extends their validity. The
proposed signed-licence design (ADR-0019, ADR-0020, security/licensing.md) needs a
signing service and its own store before any advanced feature can ship.

## Decision

- **Demo mode**: every capability that exists today works without signing in, as an open
  licence. Nothing a demo user could do before is taken away.
- **Advanced mode**: advanced capabilities require a signed-in Keycloak user (ADR-0012)
  with a valid licence that grants the capability's permission.
- **Licence record in Keycloak**: a user's licence is the user attribute
  `xds_licence_expires` (an instant in UTC) plus one client role per permission on the
  API client, starting with `ai-tools` and `change-control`. A licence without an expiry
  is invalid, never unlimited. The `xds-admin` role marks administrators, the super
  administrators of the product: it grants administration and, by the amendment below,
  every advanced capability without a licence.
- **Enforcement**: the API service validates the access token (issuer, audience,
  signature, expiry) and checks the expiry instant and the permission on every advanced
  request against its own clock. The token carries the attribute and roles through
  protocol mappers; tokens live five minutes, so a change reaches the next refresh.
  The browser shows the licence state only as information.
- **Administration**: the Admin menu calls admin endpoints of the API service, which
  require `xds-admin` and act on Keycloak through a confidential service account limited
  to managing users of the realm. Keycloak admin credentials never reach the browser.
- **Environment**: in this phase Keycloak runs locally from `infra/compose.yaml` with a
  realm imported from the repository. The published preview has no Keycloak, so it runs
  in demo mode and shows advanced capabilities as requiring sign-in.

## Amendment of 2026-09-24

Accepted by the owner, Yoshikemolo, on 2026-09-24: the super administrator, a user with
`xds-admin`, has unrestricted access to AI Tools, change control and the advanced
capabilities that follow, without holding a licence. The API grants it from the role in
the token; everyone else still needs a valid licence with the permission.

## Relation to the proposed signed licences

This decision supersedes nothing: ADR-0019 and ADR-0020 stay proposed for a later
commercial or offline phase. It deliberately differs from security/licensing.md, which
asks for signed licence envelopes and warns against using access tokens as licences.
Here the licence is the Keycloak record, and the short-lived token only carries a copy
of it. It gives no offline use, no seat counting and no proof outside Keycloak.

## Alternatives

- Signed licences with a PostgreSQL store (ADR-0019, ADR-0002). Stronger for commercial
  and offline use; more work before the advanced features.
- Licences in the local file store of the API service. A second user store beside
  Keycloak.

## Consequences

Keycloak becomes a runtime dependency of the advanced mode. Revoking or shortening a
licence takes effect within one token lifetime. Keycloak administrators can change
licences outside the Admin menu; the realm must be operated accordingly.

## Verification

SC-0134 to SC-0139 and SEC-0014.
