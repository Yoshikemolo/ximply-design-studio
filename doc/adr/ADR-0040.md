# GitHub access through the Keycloak identity

Status: Proposed, revised on 2026-09-23. The owner rejected per-user personal access
tokens pasted into Settings and directed that Keycloak be used. This revision follows
that direction; its mechanism awaits the owner's acceptance. It introduces an
authentication path, which AGENTS.md reserves for a reviewed ADR.

## Context

Pull and push to a shared GitHub repository need a GitHub credential per user. The owner
decided that users sign in to the product with Keycloak (ADR-0012) and that change
control requires sign-in and a licence (ADR-0041). A second, separate credential typed
into Settings would duplicate identity and be harder to revoke.

## Proposed decision

- GitHub is configured as an identity provider of the product realm in Keycloak, with
  its tokens stored by Keycloak. A signed-in user links their GitHub account once from
  the Keycloak account page or the first time change control needs a remote.
- For a remote operation, the API service asks Keycloak for the user's stored GitHub
  token through the broker token endpoint, with the user's own access token, which must
  carry the permission to read broker tokens. The service passes it to Git through a
  credential helper for that one operation and never stores, logs or returns it.
- Local repositories need no GitHub link. Unlinking in Keycloak removes remote access.

## Alternatives

- Fine-grained personal access tokens typed into Settings. Rejected by the owner.
- A GitHub App with the device flow. Repository-scoped and short-lived, but needs an app
  registered and operated first; it can later replace the OAuth application behind the
  same Keycloak identity provider.
- SSH keys. Key management on every host; out of scope.

## Consequences

The GitHub OAuth application behind Keycloak grants the `repo` scope, which covers every
repository the user can reach, not only the project repository; the product limits
itself to the configured remote. Keycloak must be reachable for remote operations. The
local Keycloak of this phase serves development only (ADR-0041).

## Security, operations and performance

See SEC-0013 and SEC-0014. Stored broker tokens are protected by Keycloak; the API
service holds a token only in memory for one operation.

## Migration and observability

No format change. Audit records keep the operation, remote host and result, never tokens.

## Verification

SC-0130 and the secrecy oracle of SC-0132, against a disposable remote.

Supersedes the first draft of this ADR, which proposed tokens typed into Settings.
