# FEAT-0031 — Change control with Git project history

Status: Implementing
Owner: Yoshikemolo
Iteration: ITER-0006
Dependencies: FEAT-0006, FEAT-0002, FEAT-0032
Decisions: ADR-0038 and ADR-0039 (Accepted), ADR-0040 (Proposed, revised), ADR-0041 (Accepted)
Security controls: SEC-0013
Plan: [PLAN-0031-0001](../implementation/PLAN-0031-0001.md)

## Outcome

A project, which may hold more than the current single project file, is versioned as a
Git repository in its directory, the way source code is. From the editor the designer
commits, opens and renames branches, deletes branches, merges one branch into another,
checks out branches and commits, pulls and pushes, and undoes or redoes those
operations. Several people work on the same project from their own clones of a shared
repository, local or remote on GitHub, when change control is enabled and configured in
their Settings. Every operation goes from the UI through a facade to a dedicated API of
the backend service, like the other actions of the editor.

## Functional scope

### Project directory (ADR-0038)

- A project is a directory with a manifest, one or more native documents and their
  resources. Documents are written in a canonical, stable form so that a change to one
  object changes few lines, and pixel resources are stored as separate files named by
  content hash instead of inline data, so history stays reviewable and small.
- The current single-file save keeps working. Converting a document into a project
  directory is an explicit action, never a silent migration.

### Settings > Change control category

A new Settings category, registered centrally and shown in the left column:

- Enable change control, off by default. While off, the History tab explains how to
  enable it and offers no operation. Change control requires sign-in and a licence with
  the `change-control` permission (FEAT-0032).
- Project directory, chosen inside the workspace root the API service is configured
  with; initialize a new repository or open an existing one.
- Commit author name and email.
- Remote: none, or a GitHub repository, reached with the GitHub account the user links
  to their Keycloak identity (ADR-0040). The browser never receives the GitHub token;
  the form shows whether an account is linked and can test the connection.
- Default branch name, pull strategy (fast-forward only, or merge) and an optional
  background fetch interval.

### History tab

The Change control entry of the advanced tools block in the tool rail (FEAT-0032) is the
root of this feature's tools; it opens the History tab when it exists.

Shown in the right column next to Properties and AI Tools (see FEAT-0029).

- A vertical commit graph in the style of a Git client such as GitKraken: one colored
  lane per branch, merge and fork edges, branch and tag labels, the current HEAD, local
  and remote branch badges with ahead and behind counts, and a working-copy node at the
  top when the project has uncommitted changes. The look is a behavioural and visual
  reference only; icons are the project's own SVG files under /assets/icons and no
  third-party icon, name or branding is copied.
- Selecting a node shows its details: message, author, date, SHA, parents and the
  changed files, with the documents among them.
- A right-click, the context-menu key or Shift+F10 on a node opens a context menu with
  only the operations valid for it: check out this commit, create a branch here, merge
  a branch shown on this node into the current branch, rename or delete a branch shown
  on this node, revert this commit, copy the SHA and show details.
- A toolbar at the bottom of the tab offers: Commit (message field and a summary of the
  changed files), New branch, Rename branch, Delete branch, Merge, Checkout, Pull, Push,
  Fetch, Undo, Redo and Details.

### Operation rules

- Commit saves the open documents of the project in their canonical form first, then
  commits every changed project file, or the files the designer chose, with the
  configured author. An empty message is refused.
- Checkout, merge and pull with unsaved editor changes or uncommitted project changes
  ask the designer to commit, keep or discard them first; nothing is lost silently.
  After the operation the open documents reload from the checked-out files.
- Deleting the current branch is refused; deleting an unmerged branch asks for
  confirmation.
- A merge fast-forwards when it can, otherwise it records a merge commit. Conflicts are
  listed per file; in the first slice each conflicting document is resolved by choosing
  one side, and the merge can be aborted to the state before it. The editor never opens
  a file that holds conflict markers. Object-level merging is a later capability.
- Undo and Redo in the History tab act on Git operations, separately from document undo,
  with defined inverses: a commit is undone to its parent keeping the changes; a checkout
  returns to the previous reference; a created branch is deleted; a deleted branch is
  recreated at its last SHA; a local merge is undone to the state before it. An
  operation whose commits were already pushed is not undone; the designer is offered a
  revert instead.
- Pull and push use the configured remote; a rejected push, an authentication failure
  or an unreachable remote is reported precisely and leaves local state intact.

### Delivered slice (0.13.0)

- Each project is a shared bare repository on the server; each user works in a clone of their
  own, and pull, push and fetch go through the shared repository, so several people work on
  one project. GitHub remotes wait for ADR-0040.
- A project holds one document, `documents/main.xds.json`, in canonical form, with its
  pictures in `resources/` named by hash, a manifest, `.gitattributes` and a thumbnail in
  `preview/thumbnail.png`. The API extracts and restores the pictures, so the editor format is
  unchanged.
- The History tab: the project list and a new project from the open document; the graph with
  lanes, branch badges, HEAD, a row for changes not committed and comment counts; thumbnails
  on hover (SC-0155); details with files, thumbnail and comments (SC-0156); the node context
  menu; conflicts with Keep mine, Keep theirs and Abort; and at the foot the commit field and
  the toolbar: New branch, Rename, Delete, Merge, Check out, Fetch, Pull, Push, Undo, Redo and
  Details.
- The Settings > Change control category, a choice of files to commit, tags and GitHub are
  not implemented.

### Future requirements

- Comments on pull requests, once pull requests exist (owner request of 2026-09-24). Pull
  requests and review stay excluded from this feature until the owner schedules them.

## Illustrator parity

Illustrator CS3 has no version control, so there is no behaviour or shortcut to imitate
and no default shortcut is assigned to these operations.

## Exclusions of this feature

Pull requests and code review, rebase, cherry-pick, stash, tags management, submodules,
large-file storage, SSH keys, remotes other than GitHub, object-level three-way merge of
documents, running repository hooks, and realtime presence (FEAT-0017).
